# Chat History and Run Trace Design

## Goal

Build V1 as a complete product slice for chat history and Agent run trace. A returning user should see their previous conversations by default, continue the latest session with LangGraph memory intact, and inspect the execution details behind each Agent reply.

## Scope

This version includes persistent sessions, persistent chat messages, persistent run summaries, persistent run events, API endpoints for loading history and run details, and frontend session history UI.

This version does not include password login, OAuth, organizations, billing, role-based access control, or Java services. The design must leave a clean boundary for adding or extracting those capabilities later.

## Naming and Identity Constraints

- Product and frontend naming uses `userId`, `sessionId`, and `runId`.
- Python naming uses `user_id`, `session_id`, and `run_id`.
- SQLite column naming uses `user_id`, `session_id`, and `run_id`.
- API JSON uses camelCase for identity fields: `userId`, `sessionId`, and `runId`.
- `userId` is the stable identity boundary for chat data. Today it is an anonymous ID generated by the frontend and stored in `localStorage`; later it becomes the authenticated user ID from a token.
- The backend must isolate sessions, messages, runs, and run events by `user_id`.
- `sessionId` maps to LangGraph `thread_id` for conversation memory, but it is not user identity.
- `runId` represents exactly one Agent execution caused by one user message.
- Do not encode user information into `sessionId` or `runId`.
- Do not store authentication-only fields such as password hashes, phone numbers, or OAuth provider details in chat/session/run tables.
- Keep user-system concerns behind an identity boundary so a future Java/Spring Boot identity service can own users, authentication, organizations, permissions, and token issuance.

## Architecture

Keep the Python FastAPI service as the Agent domain service for V1. It owns chat sessions, chat messages, Agent runs, and run events. It treats `userId` as an external identity value rather than a full local user account.

Introduce a small repository/service layer for persistence instead of writing database operations directly inside API handlers. This keeps the current implementation simple while making a future service split easier. If a Java identity service is added later, FastAPI should verify the token, resolve `user_id`, and continue using the same Agent-domain tables.

LangGraph checkpointer continues to store conversation state for Agent memory. The new chat history tables store product-facing messages and run trace data. These two responsibilities stay separate.

## Data Model

`chat_sessions`

- `session_id` text primary key
- `user_id` text, required
- `title` text, required
- `created_at` text ISO timestamp, required
- `updated_at` text ISO timestamp, required

`chat_messages`

- `message_id` text primary key
- `session_id` text, required
- `user_id` text, required
- `role` text, either `user` or `agent`
- `content` text, required
- `run_id` text nullable; set for Agent messages created by a run
- `created_at` text ISO timestamp, required

`agent_runs`

- `run_id` text primary key
- `session_id` text, required
- `user_id` text, required
- `user_message_id` text, required
- `agent_message_id` text nullable until the final answer is saved
- `status` text, either `running`, `completed`, or `failed`
- `prompt` text, required
- `model` text, required
- `started_at` text ISO timestamp, required
- `ended_at` text ISO timestamp nullable
- `error_message` text nullable

`agent_run_events`

- `event_id` text primary key
- `run_id` text, required
- `session_id` text, required
- `user_id` text, required
- `sequence` integer, required and increasing per run
- `event_type` text, matching SSE event type
- `payload_json` text, required
- `created_at` text ISO timestamp, required

The first production database can still be SQLite. The schema should avoid SQLite-specific assumptions where reasonable so moving to Postgres later is straightforward.

## API Design

`POST /chat/stream`

- Request adds `userId` and keeps `session_id` for backward compatibility during migration.
- Preferred request shape is `{ "userId": "...", "sessionId": "...", "message": "..." }`.
- The backend creates a user chat message, creates an `agent_runs` row with status `running`, streams the existing SSE events, saves each run event, saves the final Agent message, and marks the run `completed`.
- If the stream fails, the backend saves the error event, marks the run `failed`, and still emits the current safe error response.
- Every non-DONE SSE payload includes `runId`.

`GET /users/{userId}/sessions`

- Returns the user's sessions sorted by `updatedAt` descending.
- Supports an optional limit with a conservative default.

`POST /users/{userId}/sessions`

- Creates a new session with a generated `sessionId`.
- The initial title can be `新会话`; after the first user message, the backend may derive a short title from the message text without calling the LLM.

`GET /users/{userId}/sessions/{sessionId}/messages`

- Returns ordered chat messages for that session.
- Each Agent message includes `runId` when available so the frontend can open execution details.

`GET /users/{userId}/runs/{runId}`

- Returns run summary and ordered run events.
- Rejects access when the run does not belong to the supplied `userId`.

## Frontend Experience

The frontend generates or reads `agentHub.userId` from `localStorage`. The value should look like a real user identifier, for example `anon_user_<timestamp>_<random>`, but the app should treat it as `userId` everywhere.

On load:

1. Read `userId`.
2. Fetch the user's sessions.
3. If sessions exist, open the most recently updated session.
4. Fetch and render that session's messages.
5. If no sessions exist, create a new session and show the empty chat state.

During chat:

1. Send `userId`, `sessionId`, and message to `/chat/stream`.
2. Keep the existing real-time progress, Markdown answer rendering, and thinking state.
3. Attach the returned `runId` to the in-memory Agent message.
4. After completion, refresh or locally update the session list so the latest session moves to the top.

History UI:

- Add a left-side or compact responsive session list.
- Each session row shows title, updated time, and last-message preview when available.
- A new-chat action creates a fresh session and switches into it.
- Opening a historical session restores its messages.
- Each Agent reply exposes an execution detail action that loads `GET /users/{userId}/runs/{runId}` and renders the stored timeline using the existing summary/detail visual language.

## Error Handling

- If session loading fails, the chat surface remains usable with a visible history-load error state and a retry action.
- If message loading fails, do not delete local state; show an error for that session.
- If run detail loading fails, keep the Agent answer visible and show a detail-specific error.
- If `/chat/stream` fails after a run has been created, persist a failed run and keep the current safe frontend failure behavior.
- A missing or unknown `userId` should not reveal data. For V1 anonymous mode, the frontend creates one before calling protected history endpoints.

## Future Java Service Boundary

When a formal user system is added:

1. Java/Spring Boot can own user registration, login, organizations, permissions, and token issuance.
2. The frontend stops sending a trusted `userId` directly and sends an authorization token.
3. FastAPI validates the token or calls the identity service, extracts the canonical `user_id`, and uses it for Agent-domain queries.
4. Existing `chat_sessions`, `chat_messages`, `agent_runs`, and `agent_run_events` continue to reference `user_id` as an external identity.
5. Anonymous `userId` values can be bound or migrated to real accounts by a separate migration flow.

This V1 must not require Java, but every user-related design choice should preserve this extraction path.

## Testing Strategy

Backend tests should cover:

- Creating a session for a `user_id`.
- Listing only sessions belonging to the requested `user_id`.
- Saving user and Agent messages in order.
- Creating a run, appending ordered events, completing a run, and failing a run.
- Rejecting run detail access when `user_id` does not match.
- `/chat/stream` emits `runId` and persists events while preserving the existing SSE event shapes.

Frontend contract tests should cover:

- Stable anonymous `userId` creation and reuse from local storage.
- Loading the latest session by default.
- Mapping persisted messages into the existing chat message model.
- Associating Agent messages with `runId`.
- Rendering stored run events through the existing timeline summarizer.

Manual verification should cover:

- First-time visitor creates a session.
- Returning visitor sees previous chat history by default.
- New chat creates a separate session.
- Historical session switching preserves messages.
- Run detail opens for a completed Agent reply.
- Failed runs remain inspectable.

## Rollout

Implement this as V1 before Tool Management and Human-in-the-loop. Tool Management can later reuse run detail storage to show tool testing history. Human-in-the-loop can later persist approval and rejection events into `agent_run_events`.
